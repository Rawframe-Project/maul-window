# Gamepads

## One model, three sources of meaning

A pad is either mapped (fifteen buttons and six axes named by place) or raw (numbered controls). The meaning comes, in order of preference, from the platform (GameController, Windows.Gaming.Input, XInput, the web's standard mapping, Android's key layouts for pads it knows), from the SDL_GameControllerDB data, or from the kernel's gamepad layout on Linux for a device with `BTN_SOUTH`. Nothing is filtered: dead zones, curves and calibration are the program's, since every game wants them differently.

Rumble is a plain call, not a request: the motors start at once and the latest call wins, because a game rumbles every frame and a completion per call would only fill the queue. Motion has no records either: a 1000 Hz stream stays out of the bounded queue. The core sums every sample's rate over its time into the angle turned since the last read, counting at most 100 ms for a gap, so a pause in the stream turns nothing far and a quick flick between two frames is not lost.

## The mapping data

`tools/gamepaddb/` holds SDL_GameControllerDB as published. [tools/gen_gamepad_db.py](../../tools/gen_gamepad_db.py) compiles one platform's entries into `src/generated/pad_linux.c` and `pad_windows.c`: each device by bus, vendor, product and version, and the distinct mappings they share, where each control comes from among the device's numbered buttons, axes, axis halves and hat directions. Entries for SDL's own drivers are left out, and a later entry for a device replaces an earlier one, as in SDL. A device matches its exact version, else another version of itself. CI regenerates the tables and fails on any difference.

Linux and Windows number a device's controls as SDL does (evdev's buttons from `BTN_JOYSTICK` up then those below, axes in code order, hats apart; DirectInput's axes X, Y, Z, Rx, Ry, Rz in usage order, then sliders, hats, the Button page), so the database applies unchanged. [pad_map.c](../../src/pad_map.c) holds the mapping arithmetic both share.

## The pad tracker

Windows.Gaming.Input and GameController are runtimes that list pads and give readings. Both are driven by [pad_tracker.c](../../src/pad_tracker.c) through a table of functions: pads are looked for when the runtime says one came or went and every half second besides (the list fills only after the runtime starts, and a notification can be missed); each is read at each pump and posted only when its reading's time moves; batteries are read when pads are looked for; a rumble is stopped when its time runs out, as both runtimes keep motors running until told otherwise. Because the runtime is a table, the tracking is tested against a stand-in on every platform.

## Per platform

- **Linux** ([linux_pad.c](../../src/linux_pad.c)): evdev devices in `/dev/input`, found at the start and through inotify, retried when a node's permissions change. A gamepad has joystick or gamepad buttons and none of a keyboard's, mouse's, tablet's or motion sensor's. Events are read without blocking, stamped on the monotonic clock (`EVIOCSCLOCKID`); when the kernel drops events (`SYN_DROPPED`), what is left of the report it cut is ignored up to and including its `SYN_REPORT`, as the kernel's evdev documentation says, and the whole state is read again ([linux_evdev_drop.c](../../src/linux_evdev_drop.c)), or, where the buttons cannot be read, as when the device has gone, nothing is posted and the read error that follows closes it; the motion device does the same with its axes, and posts no sample for the cut report. Rumble is `FF_RUMBLE`. Motion comes from the second device the driver makes (hid-playstation's and hid-nintendo's), batteries from the HID device's power supply in sysfs. A motion sample is timed on the records' clock: by its report's event time, or, where the device stamps its reports (`MSC_TIMESTAMP`, microseconds that wrap), by the stamps counted from the event time of its first stamped report, so the samples keep the device's spacing; stamps that stray more than 100 ms from the event time start again from it. What the motion device hands over, its identity, resolutions and events, is read by [linux_motion_events.c](../../src/linux_motion_events.c) from plain values, so that code is tested on Linux without a device and fuzzed.
- **Windows:** Windows.Gaming.Input where `combase.dll` gives its `Gamepad` statics, which reads any number of Xbox pads with names, USB ids, batteries and trigger motors; otherwise XInput's four players, its free players asked about only every half second since asking is slow. Its interfaces are declared in the source with their ids, since the SDK's and MinGW's C declarations differ. The runtime is made for the program in the foreground and may give a background program no input. Other pads come through Raw Input on a message-only window of the pads' own, parsed by `hid.dll`; devices with `IG_` in their path are XInput's and left to it. Windows tells of a device's arrival once, so a gamepad turned away for want of room, every pad taken or the core's slot still held by a pad whose removal the program has not read, is found by reading the device list again once there is room. What the parser reads of a device, its capabilities and each report's buttons and values, is numbered and read by [hid_controls.c](../../src/hid_controls.c) from plain values, so that code is tested on Linux as well as Windows and fuzzed on Linux; its logical ranges are computed in 64 bits, since a device may give one as wide as 32 bits. A process has one Raw Input target per usage, so a program that registers joysticks itself takes them from the library.
- **macOS and iOS** ([apple_pad.m](../../src/apple_pad.m)): GameController's extended gamepad profile, read in the background too on macOS. GameController gives no USB ids. Motors are CoreHaptics engines, one per grip where the haptics reach each grip, each playing one endless continuous event whose intensity follows its motor; a failed call drops the engine and it is made again once, since CoreHaptics reports resets on a queue of its own.
- **Android:** the devices whose sources include a gamepad or joystick, listed through the library's Java helper (`InputDevice` is Java only) every half second and when an unknown device sends an event. A device is read only at the look after the one that first lists it, unless its own gamepad event brought the look: Android merges a pad's kernel devices (a DualShock 4's pad and touchpad) into one `InputDevice` as each appears, and Android 11 keeps an app's first copy of a device whose generation the merge leaves alone, so a copy read between two merges would stay a touchpad for good. On Android 12 and later its two motors play as one `CombinedVibration`, since each vibrator's own effect plays on every motor. Their keys and motions are taken from the input queue so Android's fallbacks (B as Back) do not follow. A pad with `BUTTON_A` is mapped as SDL maps Android's pads. Android gives an axis 0 until its device reports it, so a trigger on a centred axis stays at rest until it moves.
- **The web:** `navigator.getGamepads()` read at each pump; a pad's index can be reused, so disconnections are counted per index and a pad found there after one is a new pad. Name, vendor and product come from the id string, which Chrome and Firefox write differently.
