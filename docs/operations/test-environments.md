# Test environments

Every backend is tested against the platform itself where a CI runner has it, and against a stand-in of the test's own where it does not. This page says what each environment is and how to run it by hand.

## The display fixture

The X11 and weston tests, and the Linux bus tests that open an X11 window, need a display. CTest starts one for them: the `display_start` fixture runs `tools/test_display.sh`, which starts an Xvfb and, where the Wayland backend is built, a headless weston, private to the build tree; `display_stop` kills the PIDs it recorded and nothing else. The X display number comes from a hash of the build directory and weston's socket is `wayland-mwin` in `out/<preset>/rt`, which the tests get as `DISPLAY`, `WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR`. A developer's own display is never touched, and two build trees never share a server. The Xvfb runs with `-noreset`: by default it resets whenever its last client disconnects, and a test connecting during the reset would fail. The fixture is ready when Xvfb says it takes clients (`-displayfd`), not when its socket file appears, and a repeated start (`ctest --repeat`) keeps the servers it started. The fixture records each process it starts with its start time and command line, and signals a recorded PID only while both still match: the record outlives reboots and cancelled runs, and by then the PID may be another process's, perhaps another session's. A run killed or cancelled never reaches `display_stop`, so the fixture also leaves a watchdog: once the process that ran `display_start` (CTest, known by its PID and start time) is gone, the watchdog stops the servers it recorded, and it goes itself once `display_stop` has run. Start returns only once the watchdog runs its own command line: until its fork does, the process carries start's, and a start or stop meanwhile would take the fixture for gone and replace the servers. The servers and the watchdog close every descriptor they inherit, so none keeps CTest's output pipes open. `test/test_display_fixture.sh` kills a CTest-like parent with SIGKILL and checks that the servers and the watchdog are gone within 10 seconds. Since the server keeps its state from test to test, a test that changes it (output properties, RandR modes) puts it back with checked requests before it disconnects. An unchecked request's error is never seen, and requests still unanswered when a client disconnects may not be carried out: after a CRTC change, an unchecked removal of a mode sent just before disconnecting was lost. The X11 tests skip only where `DISPLAY` is unset or empty; with `DISPLAY` set, a test that cannot reach the server fails with xcb's error (`test/x11_display.h`), so a broken fixture never passes as a skip.

A server that is not installed is a platform missing. CMake looks for `Xvfb` and `weston` when it configures: without Xvfb the tests get an empty `DISPLAY` and `WAYLAND_DISPLAY`, without weston an empty `WAYLAND_DISPLAY`, and those tests skip; `display_start` skips too when a server it is asked for is not installed. Configure again after installing one. A server installed that does not start fails `display_start`. A start that fails prints the servers' logs; they stay in `out/<preset>/rt/` (`xvfb.log`, `weston.log`).

## Stand-ins

- **Wayland:** most Wayland tests run a small compositor of their own on `libwayland-server` (`test/wayland_server.h` and its protocol extensions), since a headless weston has no seat, tablet, text input or activation to drive. It records what the backend asked for: parents and positioners, grabs, idle inhibitors, icon buffers, decoration modes.
- **D-Bus:** `test/linux_bus_fake.h` starts a private `dbus-daemon` and serves stand-ins for the portal (settings, file chooser, inhibit, power profiles), the file manager, the screensaver, UPower on a private system bus, and IBus and Fcitx 5. Nothing on the machine's own buses is touched. A test that needs the bus skips only where `dbus-daemon` or libdbus-1 is absent; a bus present that does not start fails it, naming the step that failed (`FakeStart`'s outcome).
- **Programs:** stand-in `xdg-open`, `zenity` and `kdialog` scripts on `PATH`.
- **Windows:** XInput, Raw Input with the HID parser, and Windows.Gaming.Input are tables of functions the tests replace, since no virtual pad of those kinds can be made; the real runtime is still started and stopped where the system has it.
- **Gamepads on Linux:** real kernel devices made through `/dev/uinput` (the `uinput` label). Locally that needs write access to `/dev/uinput` and read access to `/dev/input/event*`.

## Windows

The Windows tests run on the runner's interactive desktop, driving it through `SendInput`, touch injection and a synthetic pen, and some change the user's settings for a moment and put them back. They run one at a time: any test's window can take the foreground another test's input needs. They also run under Wine for a MinGW build, which injects neither touch nor pen; those tests skip there. Run them with `cmake --preset windows-clang-cl`, `cmake --build --preset windows-clang-cl` and `ctest --preset windows-clang-cl` on a desktop session.

## macOS and iOS

The macOS tests need a logged-in session's window server, which CI's macOS runners have; they make the `NSEvent`s AppKit would deliver, since real input cannot be made without permissions. `cmake --preset macos-clang`.

The iOS tests run in a booted simulator: `cmake/ios-simulator.cmake` builds for it, the `ios-simulator` test preset runs `base` through `simctl spawn` as a smoke test of the build (the other test-backend suites test code `macos-clang` already runs with Apple clang on arm64, in milliseconds, against more than a second each when spawned in the simulator), and UIKit tests are applications run by `tools/run_ios_app.sh`, which installs and launches one, reads its output from a file named in its environment, waits at most three minutes for its closing line, carries out the `simctl` commands the test writes (another application launched in front of it, and its own brought back) and its `idb` commands (`ios_touch` taps the window through the simulator's own input, so CI installs idb's client and companion in the iOS job), and shows where a stuck application is (`sample`) or its crash report. On a cold runner the simulator sometimes leaves the application in the background although the launch that brings it back returned; the runner sends that launch again when UIKit has not made the application active 20 s later, twice at most, and then fails the run. Boot a simulator, set `MWIN_IOS_DEVICE` to its UDID, then use the `ios-simulator` presets. A new device's first launches take minutes. Launch Settings once after the boot, as CI does (its first launch can take over four minutes); the tests' setup fixture, `ios_warm_up` (`tools/warm_ios_simulator.sh`), then installs and launches the window test once before them, within its own five minutes.

## Android

`cmake/android-emulator.cmake` wraps the NDK's toolchain file. Executables run through `tools/run_android.sh` (`adb push`, `adb shell`); window tests are applications built without Gradle by `tools/build_android_app.sh` (javac, R8, aapt2, zipalign, apksigner) and run by `tools/run_android_app.sh`, which installs and starts one, carries out the system actions the test asks for (the home key, a rotation) and waits for its result line. The runner turns the system's animations off while a test runs and puts back the night mode, font scale, battery saver, battery and accessibility services after it. With an emulator booted, `ANDROID_HOME` and `ANDROID_NDK_HOME` set and `ANDROID_SERIAL` naming it, use the `android-emulator` presets. CI runs them in an Android 11 (API 30) and an Android 15 (API 35) emulator, the `google_apis` x86_64 images: what the backend does only from Android 12, such as a gamepad's two motors, motion sensors and battery, runs only in the second. Stop the emulator when the run ends.

## The web

The web tests run in headless Chrome through puppeteer (`test/web_runner.cjs`), found through `MWIN_NODE_MODULES`. The runner serves the build, gives each test a page and a canvas, and carries out what the test asks: a device pixel ratio or color scheme, keys, the mouse and wheel through puppeteer, touches, a pen and compositions through the DevTools protocol, a hidden page and the back-forward cache. A wasm32-wasi test is a reactor whose `main` the runner calls, with a minimal WASI and the generated imports.

`test/browser/` pins puppeteer and its dependencies in a lockfile:

```sh
mkdir -p out/browser && cp test/browser/package*.json out/browser/ && npm ci --prefix out/browser
MWIN_NODE_MODULES=$PWD/out/browser/node_modules ctest --preset web-emscripten
```
