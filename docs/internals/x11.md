# X11

X11 remains the window system of many desktops and of every remote and virtual display (Xvfb, VNC, SSH forwarding). The backend speaks XCB, never Xlib.

## Memory from XCB

XCB hands its replies over from the C library's `malloc`. They go back through [allocator.c](../../src/allocator.c), the one place the library reaches the C library's memory, so the rest of the code keeps to the context's allocator.

## Scale and windows

The scale is `Xft.dpi` from the root window's resources over 96, as desktops set it for their toolkits, else 1. The X server makes a window at once, so a creation reports it and completes in the same call. Size, place and visibility are asked of the X server and reported by its ConfigureNotify, MapNotify and UnmapNotify; a place comes from the window manager's synthetic event, else from the X server. Occlusion is the X server's VisibilityNotify: wholly covered is occluded, partly or not covered revealed, posted only when that changes. A compositing window manager redirects windows to draw them off screen, and the X server then reports every redirected window uncovered, so under one the window is never occluded.

Modes belong to the window manager. A mode request asks it through `_NET_WM_STATE` (or ICCCM's `WM_CHANGE_STATE` to minimize) and is answered done when the property shows the mode, denied after half a second. Without an EWMH window manager, mode requests are unsupported. A window manager counts only when the root's `_NET_SUPPORTING_WM_CHECK` names a window that names itself, so a property left behind by a window manager that quit does not count. Xvfb has no window manager, which is how the tests see both paths.

## Monitors and HDR

Monitors come from RandR 1.5's monitor list, keyed by the atom of their name; without RandR 1.5 the screen is the one monitor. HDR luminances come from the RandR `EDID` output property through the shared parser ([edid.c](../../src/edid.c)), which checks every block's checksum and length; X11 has no HDR output, so HDR is never on. Variable refresh is the `vrr_capable` property.

## XInput 2: one path for the pointer

The X server gives an event to a client in one form only, so reading scroll valuators means reading all pointer events of a window from XInput 2. With XI 2.1 or later, each window selects the XI2 button and motion events of the master pointers, and each is read as the core event it stands for, so the pointer keeps one code path; enter, leave and keys stay core events.

- **Smooth scrolling** ([x11_scroll.c](../../src/x11_scroll.c)): the scroll valuators of slave pointers, read with `XIQueryDevice` at the start and on hierarchy and class changes, give fractional wheel turns. The first value after the pointer enters or the master switches devices only starts the count. Wheel buttons flagged as emulated are dropped.
- **Touch** ([x11_touch.c](../../src/x11_touch.c)): XI 2.2 touch events, selected with the pointer events, carry each touch's id and valuators, and the server then emulates no pointer for them. Devices with a direct touch class are touch screens. A client without a grab gets a touch's events only once it owns it, so no touch is ever cancelled on X11.
- **Pens** ([x11_pen.c](../../src/x11_pen.c)): X11 has no tablet protocol. A tablet driver's slave pointers of input type `STYLUS` or `ERASER` are pens; one of type `TABLET` or none is a pen by an eraser in its name, then by an `Abs Pressure` valuator. Other types are never pens, since touch screens carry a pressure valuator too. Each valuator keeps its last value, as an event carries only the changed ones.
- A captured cursor is a hidden one confined to the window's middle, with XI2 raw motion as the deltas; without XInput 2, capture is unsupported. A caption press for custom chrome first gives up the X server's grab and the XI2 device grab, then asks the window manager to move the window.

These modules take device descriptions and event bytes, not a connection, because Xvfb has no touch screen, tablet or scroll classes; their tests feed them written-out devices and events.

## Selections, drops and input methods

The clipboard and the primary selection are served by a hidden window of the context's own; drops speak XDND 5 ([Clipboard and drops](clipboard-and-drops.md)). Input methods are IBus or Fcitx 5 over the session bus ([Text input](text-input.md#x11-ibus-and-fcitx-5-over-d-bus)).
