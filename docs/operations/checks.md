# Checks

What verifies a change, locally and in CI, and the time each may take.

## Locally

`tools/check.sh` runs the Linux checks in three tiers; each includes the one before it. Its builds are the CI cells' presets from `CMakePresets.json`, in `out/<preset>`, and the other trees go to `out/check-*`, each with its log beside it.

| Tier | Runs | Budget |
|---|---|---|
| `changed` | The source, module, length, API documentation, snippet and test hygiene rules, the organization's documentation check, `clang-format` on the changed C and Objective-C files, clang-tidy in a Release build and a Debug build on the changed `src/*.c` files among the Linux build's sources (`src/generated/` left out, as in `pr`), the iOS runner's test when an iOS script changed, and in the `linux-clang-20-asan` preset that every test carries a label and the tests whose labels the changed files reach, integration tests left out. | under 2 minutes on built trees |
| `pr` | Every rule on every file, the generated tables against their generators, the iOS runner against a stand-in simulator (`tools/test_run_ios_app.sh`), that the documentation site builds, clang-tidy over the Linux build's sources in a Release build and a Debug build, the whole `linux-clang-20-asan` suite with the display fixture, and 10 seconds of fuzzing per target. | under 10 minutes |
| `full` | Also the other Linux presets (ThreadSanitizer, shared, minimal, Clang and GCC Release), each with its tests' labels checked, the virtual gamepad tests where `/dev/uinput` can be written, and 60 seconds per fuzz target. | under 20 minutes |

Run `changed` before every push. On the shared development machine, run `pr` and `full` through the workspace's heavy-job wrapper. The macOS, iOS, Android, Windows and web cells run in CI; [Test environments](test-environments.md) says how to run each by hand.

## Tests and labels

Each suite is `test/test_<name>.c` (or `.m`), one executable registered with CTest as `<name>` and labeled `<name>`, so `ctest --preset <preset> -L <name>` runs one. Other labels:

- `integration`: tests that drive a real window system, server, device, simulator, emulator or browser: the X11 and weston tests against the display fixture, the Wayland tests against a stand-in compositor on a thread of their own, the Linux bus tests, the virtual gamepad tests, and every macOS, iOS, Android, Windows desktop and web test. They may read the clock, take about a second each, and stay out of the `changed` tier.
- `quarantine`: a test that failed intermittently, labeled through `maul_add_test(... QUARANTINE)` or `maul_quarantine(<test>)`. Every test preset and `tools/check.sh` leave it out, and each platform's nightly runs it through `tools/run_quarantine.sh`: the `quarantine` job on Linux, macOS and Windows, the `gamepads` job for the virtual pads, and a step of the iOS, Android and web jobs. Its failure is a known flake, reported as a warning and in the job summary without failing the night; a skip, a test that did not run, a sanitizer report or a crash on a bad address fails the night. It leaves quarantine when the fix of the issue named in the comment above its label has landed and the nightly run has passed it 14 nights in a row. It is never retried.
- `uinput`: the tests that make virtual gamepads through `/dev/uinput`. A container job has no input devices, so the Linux test presets leave them out; the `full` tier runs them where the device can be written, and CI every night.

The Linux tests that need a display get the build's own Xvfb and headless weston from the display fixture ([Test environments](test-environments.md#the-display-fixture)); the stand-in compositors and buses need nothing installed but what the image has. Without integration tests the `changed` tier runs the contract on the test backend and the modules that take plain values, which cover most of the core. A test that cannot run exits 77, which CTest reports as skipped, and every CI cell fails on a skipped or unrun test, so a platform that did not start never passes with nothing tested. A skip is only for a platform that is missing (no display, no runtime folder, no input devices); a test whose own setup fails, such as a temporary folder or its stand-in compositor, prints `FAIL:` with the reason and fails. A failed test job uploads its CTest logs, kept for a week.

A test never sleeps, reads the wall clock, tries again or skips without saying why: `tools/check_test_hygiene.py` rejects each, and every test registered without a label. A use that must stay carries `// hygiene: <reason>` (`# hygiene:` in CMake) on its line or the one before. Here those are the pauses of a frame loop or a poll while a server, a bus or another thread answers, each ended by what it reports within the test's deadline; the skips for a missing platform, which CI fails; input left waiting in Windows' queue on purpose; and one try again, saying why where it is: the X11 input method's key order. The iOS runner (`tools/run_ios_app.sh`, not scanned) also sends the launch that brings an application back again, twice at most, when the simulator leaves it in the background; that is the simulator's to do, and what the test checks starts once UIKit makes the application active.

## In CI

`.github/workflows/ci.yml` runs on every pull request, every push to `main` and every night. The Linux jobs run in the organization's CI image, pinned by digest, and install nothing. The ruleset requires only its `required` job, which passes when every other job passed or was skipped, and the title check.

| Job | What it guards |
|---|---|
| `changes` | Whether a pull request changes anything beyond documentation; when it does not, the build jobs are skipped. |
| `docs` | The organization's documentation check, run from the pinned commit of `.github`. `protocols/`, `tools/gamepaddb/` and `tools/androidkeys/` hold third-party files and are excluded. |
| `zizmor` | The workflows: injection, persisted credentials, permissions, unpinned actions. |
| `checks` | `clang-format`, the family's rules, test hygiene and that every test the Linux, shared, minimal and wasm32-wasi configurations register carries a label, that the documentation site builds, that the gamepad and Android key tables match their generators, the iOS runner against a stand-in simulator, and clang-tidy (`tools/run_tidy.sh`, as many files at a time as the runner has cores, each file's result in order and a failing file named), over a Release build, where the assertions compile out, and a Debug build, where they trap: each hides paths from the analyzer that the other shows. It runs on documentation changes too. |
| `build` | One call of the organization's `cpp.yml` per preset: GCC 14 and Clang 20 in Release, Clang with AddressSanitizer and UBSan (each test repeated up to three times on a pull request, so a flaky one fails before it merges), Clang with ThreadSanitizer, the shared library, the test backend alone, macOS on its runner and `clang-cl` on Windows. All build with warnings as errors. |
| `msvc-headers` | Every public header compiled by MSVC's `cl` as C17 and C++17 with `/W4 /WX`. |
| `fuzz` | Each fuzz target in a job of its own, from its committed seeds and the corpus `fuzz-nightly` keeps for it, restored read-only: 20 seconds each on a pull request, 90 on `main`. A change that breaks a harness's promise fails on its own pull request. |
| `fuzz-nightly` | Every night, each fuzz target in a job of its own for 600 seconds, from its corpus of the nights before ([Fuzzing](#fuzzing)). Not part of the required check. |
| `ios-simulator` | The iOS backend and its tests built on every pull request; on `main` and at night, its UIKit tests and `base` (the test-backend suites run in `macos-clang`) run on an iPhone simulator of the newest runtime, then the window test and `ios_scenes` (several scenes) on an iPad of that runtime, one device booted at a time (`tools/ci_simulator.sh` picks each, and fails when the runtime has none). A simulator's boot and first launch take longer than the pull request budget leaves. |
| `android-emulator` | The Android backend in Android 11 and Android 15 emulators on the Linux runner with KVM. |
| `web-wasi` | The web backend built by Clang for wasm32-wasi in the CI image, every test a module in headless Chrome with the generated JavaScript imports. |
| `web-emscripten` | The web backend built by Emscripten, its tests in headless Chrome through puppeteer, and what the backend adds to a program's size. |
| `gamepads` | Every night: the virtual gamepad tests, in the CI image run by `docker` with the runner's `/dev/uinput` passed in. A skipped test fails it. |
| `prune-caches` | On `main` only, after every job that saves a cache: the organization's `cache-prune.yml` deletes the cache entries a newer save of the same key replaced ([caches](#caches)). |
| `quarantine` | Every night: the quarantined tests of `linux-clang-20-asan` (the virtual pads aside), `macos-clang` and `windows-clang-cl` through `tools/run_quarantine.sh`, with the test presets' timeout. |

Every job that compiles on a pull request restores a ccache of its own, as `cpp.yml` does for its cells, and only `main` saves one, so a pull request reads the latest `main` cache and never writes. The CI image carries ccache; `android-emulator` and `ios-simulator` take a pinned release binary checked against its hash. `web-emscripten` has none: its build time is linking (`wasm-opt` on each test), which ccache does not cache. Each build prints ccache's hits and misses. `android-emulator` also restores its pinned NDK, which the runner image does not carry, from a cache keyed by the NDK's version: the SDK manager installs it only on a miss, and only `main` saves it.

### Caches

A ccache is saved under a key that ends in the commit, and a corpus under one that ends in the run, so each save adds an entry, and the repository's 10 GB would fill within a day. GitHub then evicts the least recently used entries, which can be a corpus only the next night restores. `prune-caches` runs after every job that saves a cache, on `main` only: it deletes each entry of `main` whose key, up to that commit or run, a newer entry shares, and keeps every other entry and every entry of another branch.

`pr-title.yml` checks that the pull request title is a conventional commit with a scope from `AGENTS.md`, and `pr-gate.yml` closes a pull request from outside the organization unless it closes an issue labeled `accepted`. `codeql.yml` runs CodeQL in the CI image on every pull request and on `main`. `scorecard.yml` grades the repository's security practices weekly, and Dependabot proposes updates of the pinned actions once a week.

## Fuzzing

The fuzz targets (`test/fuzz_<area>.c`, built with `-DMAUL_WINDOW_FUZZ=ON` and Clang on the test backend) cover the bytes other programs and devices hand the library: EDID blocks, payloads (`text/uri-list`, dropped and pasted text in UTF-8 and UTF-16, zenity's output), compositions, POSIX locale names, X11 scroll valuators, gamepad reports through their mapping, a HID gamepad's capabilities and reports as Windows' HID parser gives them (`fuzz_hid`: any page, usage range, size and logical range, and reports of any values and sizes), a Linux gamepad's battery charge as the kernel's capacity file gives it (`fuzz_battery`: text of any bytes and length), a Linux gamepad's motion device (`fuzz_linux_motion`: two devices' identities, the axes' values and resolutions, and evdev events of any type, code, value and spacing, the kernel's drops among them), the X11 clipboard and primary selection reads (`fuzz_x11_selection`: the owner's answer, the property whole or in INCR pieces, and the events other clients cause meanwhile, against a stand-in X server), the X11 drag and drop (`fuzz_x11_drop`: the XDND messages any client can send to any window, the source's type list, and the answers to a drop's conversions, of any type, format and length), and the Wayland data offers (`fuzz_wayland_offer`: the type lists of the clipboard's, the primary selection's and a drag's offers, and the bytes their clients send through the pipes, in pieces, cut short or past the limits, against a stand-in compositor), the Wayland input method's events (`fuzz_wayland_text`: enter, leave, preedit and commit strings of any bytes and length with any cursor offsets, delete-surrounding of any lengths and done, as windows turn text input on and off and go), and the D-Bus messages of the Linux services and input methods (`fuzz_linux_bus`: the Settings portal's, the file chooser's, the power profile monitor's and UPower's replies and signals, the screensaver's and the inhibit portal's answers as the wish to keep the display awake comes and goes, Fcitx 5's and IBus's input contexts, key answers, commits and compositions, of the shapes the modules expect with other types in their place, built and read back by libdbus on stand-in connections), and the web page's records (`fuzz_web_records`: every field of a record and every string beside it, which other scripts on the page can reach, through the web backend's C files built for the host). Each checks properties that hold for any input: no crash, text kept within its limit and valid UTF-8, a composition's offsets on character boundaries and fitting idempotent, sticks and triggers within their ranges, a HID gamepad's buttons each numbered once and its hats one of their eight steps or centred, a raw input's reports within its bytes, a battery's charge read only from a whole number from 0 to 100, and never past the text's length, a motion sample holding each axis's last value in the contract's frame, at its event time or, when stamped, within 100 ms of it, every clipboard request answered exactly once, each window's drag records in order and every drop taken finished once, a drop cut short marked truncated, no Wayland object used after the backend destroyed it, no offer and no pipe left behind, each window reading exactly the input method's records a done should give, in order, its text repaired to UTF-8 and a reset where a string was lost, a D-Bus value of an unexpected type left alone, every bus call and filter let go, each inhibition of the display held alone and let go exactly once, the facts in range, each key offered to an input method read at most once, in the order offered, and only for the window it was offered for, and positions, sizes, scales, pressures and outcomes from the page within the contract. A crash a fuzzer finds becomes a test in its module's suite ([Development](development.md#a-fuzz-finding)).

Each target starts from its committed seeds (`test/seeds/<target>/`), inputs that reach what random bytes rarely would. The nightly run also carries a corpus per target from night to night in an Actions cache, which every run restores, a pull request's included; only a clean nightly run on `main` saves it:

- The cache key is the target and the run that saved it (`corpus-<target>-<run id>`), and every run restores the target's newest. The key names no build: a corpus is only inputs, which stay valid against a new binary, and the merge re-scores them. A key per build would also leave an older build's corpus where `prune-caches` never deletes it.
- After its 600 seconds, the fuzzer's merge step minimizes the seeds and the corpus together, keeping the files that still reach every feature either reaches (some of them seeds), and that is saved for the next night. The merge runs through `tools/fuzz_target.sh --merge`, which prints one line and fails when an input crashes, reporting the finding as a run does without its input. A run or a merge that found something saves nothing.
- The run's summary says which corpus was restored (the run that saved it, or none) and gives the seeds' coverage beside the corpus's. Where the corpus reaches more, the inputs worth keeping are found locally and committed as seeds ([Development](development.md#a-fuzz-finding)).
- Every run, on a pull request, on main and at night, goes through `tools/fuzz_target.sh`. A finding is reported by its kind and its sanitizer report, never by its input, its seed or its file name, and the finding and the target's log stay on the runner. No job uploads a finding, a fuzz log or a corpus. `fuzz` restores the target's corpus as `fuzz-nightly` does, and prints which one it got, but never saves or minimizes it.

## Budgets

Over a budget, tests are pruned or merged before anything else is added. The pull request check's longest job is the Android emulator (about five minutes); the whole Linux suite runs in a few seconds once built. The iOS simulator run (eight to eleven minutes on the iPhone, most of it booting, then the iPad's boot and its tests) is on `main` and at night.
